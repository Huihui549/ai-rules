# R3 协作与修改流程

## 意图边界（何时才允许动文件）

- 用户咨询、请教思路、询问方案 → **只输出建议**：说明思路、技术讲解、指出"需修改哪个文件的什么位置"
- **禁止**：新建项目演示、创建文件、修改用户文件、运行有副作用命令
- 仅当用户话中**明确要求修改/创建**（"帮我改/实现/添加/删除/新建"等动作指令）才允许动文件
- 含糊表述（"你看怎么办""有什么办法""帮我看看"）一律按咨询处理，不修改
- 意图不明 → 默认**不修改**，先向用户确认
- 用户提出修改时，先确认影响范围再动手，避免连锁改动失控
- 修改任何文件前，须满足 git 前置要求（见 R4）
- 理由：未授权的修改难以察觉且可能破坏现有内容；咨询场景的合理输出是"信息"而非"变更"
- 授权范围内的必修问题按 R1 第三节自治处理：直接改完并一行报告，**不得**把改法选择推回用户（边界见 R7 冲突表）

## 编码任务五步

1. **复述确认**：先复述需求与验收标准，用户确认后才动手
2. **计划先行**：列出改动文件清单与实现步骤（含每步验证方式）
3. **小步实现**：任务拆成可独立验证的小块，逐块完成
4. **验证闭环**：每步运行测试/编译/静态分析，通过才继续
5. **最小改动**：只改与任务相关的文件，不顺手重构、不格式化无关代码

## 完成时自报（三行式）

- 改动了哪些文件，每处原因
- 哪些部分是假设/猜测
- 如何验证（编译 / 单测 / 逻辑推演）

## 批量任务逐条推进（多条命令/功能/任务逐一处理时，强制执行）

| 规则 | 说明 |
|------|------|
| 先提问后修改 | 每条任务先列出需要确认的问题（参数来源、边界条件、UI 表现等），确认完毕才动手 |
| 一次只问一个问题 | 每次只提一个问题，确认后再问下一个；严禁一次性抛出多个问题 |
| 逐条推进 | 一条确认并实现完毕后，再进入下一条；绝不批量处理 |
| 帮助打开思路 | 提问应覆盖用户可能遗漏的细节，帮助补充完善方案 |
| 明确指令才动手 | 即使问题已全部确认，用户明确发出修改指令后才写代码 |

## 注释保护原则（强制执行）

- **注释无错不删**：注释没有事实性错误、不需要更改时，不允许删除或缩短
- **重构不丢注释**：提取函数/拆分代码块时，必须将原有注释原样搬运到新位置
- **违反即回退**：发现注释被无端删除的改动，立即回退重做
