# R8 工程代码卫生（防屎山）

> 最大风险不是写错代码，而是持续"无脑叠加"：每次加一点、不清理、再叠一层，三个月后无人看得懂。

## 改动边界（呼应 R3 最小改动）

- 只做目标**最低限度必要**的改动：不改无关代码、不顺手重构、不统一老代码风格（不合规范也先记 TODO）、不扩展未明确的需求
- **判断标准**：不做这项改动，目标仍能完成 → 不做
- 必须同步的例外：同一逻辑出现在 3 处以上 → 提取为单一函数；改了 public 签名 → 同步所有调用方

## 删除优先（删比加更重要）

| 规则 | 禁止 |
|---|---|
| 删除，不注释保留 | `// oldMethod(); // 保留备用` |
| 废弃接口立即删 | 方法/信号/属性不再被调用 |
| 不留向后兼容 | 重构后新旧接口不得共存 |
| 无用成员立即删 | 有写入无读取 |
| 重复代码必提取 | 同一逻辑 ≥3 处 |

**铁律**：重构时删除行 ≥ 新增行；新增功能时代码量与复杂度成比例。

## 禁止项

- **YAGNI**：不预留参数、接口、分支；现在没人用 → 不写
- **过度抽象**：第 2 次仍复制、第 3 次才提取；不封装单次库调用；只有一个实现类的接口/基类不要存在；禁止 `a->b()->c()->d()` 跨层链式调用
- **诡代码**：位运算传 bool 标志（硬件寄存器除外）、隐式类型转换（`float x = 1/2`）、双重否定（代码与中文表述都禁止，表述侧见 R1 第四节）、无注释长正则（>10 字符）、`goto`

## 屎山堆积模式（评审发现即退回）

| 行为 | 正确做法 |
|---|---|
| 复制函数只改 3 行 | 提取公共函数 |
| 原函数里追加 `if (新条件)` | 策略/状态模式 |
| 类属性从 5 个涨到 20 个 | 拆类 |
| `#include` 只增不删 | 定期清理 |
| 日志无开关散布 | 日志分级 + 编译开关 |

## 性能金律（性能敏感路径，强制）

- **指标先量化**：性能敏感需求必须在 `spec.md` 写成数字（响应时间、帧周期、CPU 占用），没有数字就不算需求
- **改完必测、测必记录**：前后数据在同一平台、同一编译配置下测得；记录进 `dev.md`
- **不得交出未测的性能敏感路径**：无法直接测时用打点手段——周期计数器（如 DWT）、GPIO 翻转配示波器/逻辑分析仪、串口时间戳
- **不得凭感觉说"很快"**：断言性能必须附实测数据（R2）
- 不改没证明瓶颈的代码；优化中不顺手重构；收益 <10% 的微优化一般不值得，除非有充分理由
- 热路径禁区（逐项目可加细）：动态分配、逐帧大块拷贝、热路径里做字符串格式化/日志、重复浮点重算、阻塞式延时、逐字节 I/O、无界循环

## CR 必查（每次代码审查）

- 无"可能以后用到"的预留代码；新增类/函数/属性都有明确调用方
- 无复制粘贴仅改几行的代码块；重构时删/增比健康
- 性能对比数据在同一平台/编译配置下测得

## 优先级

| 级别 | 含义 |
|---|---|
| P0 | 本规则"强制"项——违反即不允许合并 |
| P1 | 优先/推荐——无充分理由不得违反 |
| P2 | 平台/框架官方惯例——P0/P1 未覆盖时默认遵循 |
| P3 | 经用户确认的临时/特殊约定 |
