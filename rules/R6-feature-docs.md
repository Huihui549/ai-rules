# R6 功能开发文档

## 目录边界

- `ai-rules/`：只存放**绝对通用**的规则与模板；任何项目/功能相关内容**禁止**放入
- 功能开发文档统一存放：`dev-docs/<项目名>/features/<功能名>/`（工作区根，与 ai-rules 平级；每个项目一个目录）
- git 保障：功能文档所在目录必须位于 git 仓库内（见 R4）

## 自动流程（无需用户提醒）

每开发一个功能，自动执行：

1. **开始前**：创建 `dev-docs/<项目名>/features/<功能名>/`，写入需求文档（复用 `templates/task-prompt.md` 结构：任务/输入/处理/输出/边界/约束/验收）
2. **过程中**：每完成一个可验证步骤，更新文档（实现要点、验证结果）
3. **完成后**：自动执行三件事——
   - **审查**：对照验收清单逐项检查文档完整性
   - **总结**：输出功能总结（做了什么、关键决策、遗留问题）
   - **精简**：删除过程噪音，只保留结论与可复用信息

## 文档结构（单文件 `feature.md` 起步）

1. 需求（含验收清单）
2. 实现（改动文件、关键决策）
3. 验证（测试/编译结果）
4. 总结（结论、遗留项、经验）

## 补充约定

- 功能文档记录"决策与结果"，不写流水账
- 每功能完成后，若产生**通用**经验 → 按 R7 流程提炼入 ai-rules
- 用户未要求时也自动执行上述流程，不等用户提醒

## 文档写作规范

### 思行分离（强制）

撰写技术文档时，"思想/逻辑"与"操作步骤"严格分离：

| 区域 | 内容 | 要求 |
|------|------|------|
| 思想/逻辑 | 背景、根因、执行链路、为什么这样做 | 串联完整逻辑闭环，清晰说明因果关系 |
| 操作步骤 | 改哪个文件、加哪行代码、执行什么命令 | 极简编号列表，一行一件事，不混入解释 |

> 先讲清"为什么"，再列出"怎么做"；操作步骤中不穿插原理解释，思想部分不夹杂执行细节。

### 文档粒度（按读者分两档）

| 读者 | 规则 |
|------|------|
| 人（默认） | 完整句子、带注释代码、层级清晰 |
| AI（文件名带 `-ai` 后缀） | 精简风：砍层级、砍解释、砍冗余代码块；一句话能说清不写一段，一个表格装下不拆两个；目录深度 ≤ 2 |

### 文件命名规范（新创建文件强制按此格式）

格式：`[功能码]-[简短描述][-读者].md`

| 段 | 说明 | 示例 |
|----|------|------|
| 功能码 | 2-5 字母缩写，标识文档类型 | `dev` `log` `plan` `spec` `debug` `guide` |
| 简短描述 | 中文或英文，一眼看懂主题 | `<项目名>` `<模块升级>` |
| 读者（可选） | `-ai` 表示给 AI 看的，省略则默认给人看 | `spec-助手角色-ai.md` |

功能码表：

| 功能码 | 含义 | 适用场景 |
|--------|------|---------|
| `dev` | 开发文档 | 功能实现记录、开发过程说明 |
| `log` | 开发记录/日志 | 每日开发动态 |
| `plan` | 计划书 | 升级、移植、改造方案 |
| `spec` | AI规范/设定 | 角色设定、编写规范等 AI 上下文（带 `-ai`） |
| `debug` | 调试/排查 | 问题定位、根因分析 |
| `guide` | 操作指南 | 构建步骤、工具使用 |

### 路径标注设备归属（强制）

- 文档中任何路径必须标明所属设备：正文用 `[开发板]` / `[PC]` 前缀，表格加"位置"列
- 示例：`[开发板] /opt/app/bin/xxx`；`[PC] /opt/toolchain/bin/qmake`
- 理由：同一路径在不同设备含义不同（如 `/opt` 在 PC 是 SDK、在开发板是部署目录；`/tmp/xxx` 可能是 PC 脚本或开发板信号文件），不标注会误执行、误读
