# R6 项目文档体系

## 目录边界与位置

- `ai-rules/` 只放**绝对通用**的规则与模板；项目/功能相关内容禁止放入（R7 归置判断）
- 项目侧：项目根 `AGENTS.md` + 项目根下的 `dev-docs/<项目名>/`（须在 git 仓库内，R4）
- **位置决策**：文档就放**项目根的 `dev-docs/`**，与代码同一个仓库、同一个版本历史——AI 经 `AGENTS.md` 自然读到，改动随代码一起回溯
  - 不用独立的文档目录/独立仓库：跨目录跨盘易失同步，且 AI 常读不到（例外：团队强制要求独立文档库时，必须在 `AGENTS.md` 写明路径，并保证每轮能被读到）

## 两级结构（判据：这条内容**会不会跨功能复用**）

```
<项目根>/
├── AGENTS.md                        ← 项目级：AI 协作须知
└── dev-docs/<项目名>/
    ├── context.md                   ← 项目级：这个项目是什么
    ├── pitfalls.md                  ← 项目级：跨功能的坑总表（只增）
    ├── adr/0001-<主题>.md           ← 项目级：决策记录（只增）
    ├── requirements/ design/ ops/   ← 项目级：大需求 / 选型 / 运维
    └── features/<功能名>/
        ├── spec.md                  ← 功能级：需求 + 验收标准（冻结）
        ├── verify.md                ← 功能级：可执行命令 + 真机验收项
        └── dev.md                   ← 功能级：可重放开发日志
```

| 级别 | 文件 | 放什么 | 谁写 | 何时建 |
|---|---|---|---|---|
| 项目级 | `AGENTS.md` | 硬事实：构建/烧写/测试命令、**远程运行与自动化边界**（SSH、串口、日志、固件备份、人工步骤）、目录职责、硬约定、禁区、`ai-rules` 路径 | 用户主写，AI 可提议与索要 | 首次接触该项目 |
| 项目级 | `context.md` | 技术栈、芯片、工具链、关键路径、硬性约束 | AI 填、用户审 | 首次接触该项目 |
| 项目级 | `pitfalls.md` | 跨功能的坑（时区、编码、脚本陷阱…），每条注明来源功能 | AI 自动追加 | 踩到即写 |
| 项目级 | `adr/NNNN-<主题>.md` | 决策：为什么选 A 不选 B | AI 写 | 有取舍时 |
| 功能级 | `features/<功能名>/spec.md` | 需求与验收：输入→处理→输出、边界与异常、验收清单 | AI 写、用户确认 | 开工时 |
| 功能级 | `features/<功能名>/verify.md` | DoD：构建/测试/静态检查命令 + 真机项 | AI 起草、用户补真机项 | 随 spec 一起 |
| 功能级 | `features/<功能名>/dev.md` | 可重放开发日志（见「日志写法」） | AI 自动维护 | 实现第一步起 |

- 坑与决策放**项目级**的理由：它们的价值在于被后续功能复用；埋在 `features/<功能名>/` 里，别的功能翻不到
- 双向可追：`dev.md` 里写「坑 #12」「ADR-0003」，`pitfalls.md`/`adr` 每条注明来源功能

模板：全部在 `templates/project-skeleton/`（README.md 给出每个模板的目标路径），整目录复制后按 README 放置。

## 自动创建与维护（无需用户提醒，强制）

| 触发 | 必须自动做 |
|---|---|
| 会话首次接触某项目 | 缺 `AGENTS.md` / `dev-docs/<项目名>/` → 按骨架补齐（含 `context.md`、`pitfalls.md`、`adr/`），已知信息直接填入，然后报告 |
| 首次接触 + 运行配置缺失 | **主动向用户索要**：交叉编译命令与环境、SSH 方式（是否免密）、烧写/启动命令、串口设备与波特率、日志抓取方式、固件备份位置、只能人工做的步骤 → 写入 `AGENTS.md`「构建/运行/测试」与「远程运行与自动化边界」；**缺项不得猜测**，先问 |
| 开始一个新功能 | 创建 `features/<功能名>/`，写入 `spec.md`（需求+验收）与 `verify.md` 草案 |
| 每轮有重要更新 | 检查并更新对应文件：需求变更→`spec.md`；验证推进→`verify.md`、`dev.md`；踩坑→`pitfalls.md`；取舍→`adr/` |
| 会话收尾 | 补齐上述未落笔的内容（R5 收尾回填），对照验收逐项打勾 |

- 报告方式：只列新建/更新了哪些文件 + 每条一句，不复述内容
- 边界（R3）：首次接触项目时用一句"我按骨架建这些，可以吗"取得授权；已授权项目内直接做，不再逐次请示

## 自动流程（无需用户提醒）

1. **开始前**：按 `templates/project-skeleton/spec.md` 写 `spec.md`，用户确认后冻结需求与验收标准
2. **过程中**：每完成一个可验证步骤 → 跑 `verify.md` 里的命令 → 结果写进 `dev.md`
3. **完成后**：对照验收清单逐项打勾 → 总结（做了什么、关键决策、遗留项）→ 删过程噪音，只留结论与可复用信息 → 逐行自审本轮 diff（R1 第七节第 7 项）
4. **修 bug 必补回归项**：每个修好的 bug，把复现步骤固化成 `verify.md` 里的一条检查（命令或真机步骤），使该 bug 不会回来
5. **收尾回填**（会话末，见 R5）：新坑 → `pitfalls.md`；决策 → `adr/`；新验收标准 → `verify.md`

## 日志写法（可重放，强制）

- 按**功能单元**分节（依赖序），每单元含：目标 / 改动 / 事实（协议、数据、接口）/ 验证结果 / 依赖
- 单会话多个小功能**不得**合并成一段笼统叙述；不写按时间的流水账

## 文档写作规范

### 思行分离（强制）

| 区域 | 内容 | 要求 |
|---|---|---|
| 思想/逻辑 | 背景、根因、链路、为什么这样做 | 完整逻辑闭环，因果清楚 |
| 操作步骤 | 改哪个文件、加哪行、跑什么命令 | 极简编号列表，一行一件事，不混解释 |

先讲清"为什么"，再列"怎么做"；操作步骤不夹原理，思想部分不夹执行细节。

### 分层与分类说明必须分段

- 先总览表（层 → 是否修改 → 概要），再分节展开；"要改的"与"不动的"分组呈现
- 同一层用固定结构（职责 → 原因 → 何时才动）；**严禁多层混写在一段**

### 粒度（按读者分两档）

| 读者 | 规则 |
|---|---|
| 人（默认） | 完整句子、带注释代码、层级清晰 |
| AI（文件名带 `-ai`） | 精简：砍层级/解释/冗余代码；一句话说清不写一段；目录深度 ≤2 |

### 命名

- 项目级固定名：`context.md` `pitfalls.md` `adr/NNNN-<主题>.md`；跨功能长文 `<功能码>-<简短描述>[-ai].md`，功能码：`plan`（方案）/ `log`（日志）/ `debug`（排查）/ `guide`（指南）
- 功能级固定名：`spec.md` `verify.md` `dev.md`

### 路径标注设备归属（强制）

- 文档中任何路径必须标明设备：正文用 `[开发板]` / `[PC]` 前缀，表格加"位置"列
- 例：`[开发板] /opt/app/bin/xxx`；`[PC] /opt/toolchain/bin/qmake`
- 理由：同一路径在不同设备含义不同，不标注会误执行
