# R7 规则维护

## 命名约定

- 任何"字母数字代指简称"（如 R1、SKILL-A）一旦用于指代文件，**必须**作为该文件名前缀
- 目的：打开目录即识别文件身份；示例 `R1-output.md`；无简称文件不受影响

## 归置判断（教训该去哪）

| 内容 | 归属 |
|---|---|
| 本项目的坑、决策（跨功能复用） | 项目级：`dev-docs/<项目名>/pitfalls.md` / `adr/`（R6） |
| 本次功能的需求与验收、验证命令 | 功能级：`features/<功能名>/spec.md` / `verify.md`（R6） |
| 跨项目通用的**行为**约束 | `rules/`：并入现有规则，确需新建再建 `R<编号>-*.md` |
| 用户肯定的回答、通用教训 | 归属规则文件 / `logs/lessons.md` |

- **升格门槛**：项目侧的坑要变成规则，必须满足「**跨项目适用 且 出现 ≥2 次**」；单次的项目坑只留在项目侧
- **自动积累（触发）**：开发中遇到有用且通用的约束，自动补充，不等提醒；这是 R3 授权边界的例外，仅限 `ai-rules/` 自身文件与本项目文档的收尾回填（R5）

## 单一事实源（SSOT，防左右脑互搏）

- 每条规则的**全文只写在其归属文件**；其他文件（规则、模板、README、logs）只允许"编号 + 一句标签"引用，**禁止重述细则**
- 同一约束两处表述不一致 → 以 `rules/` 原文为准，改写或删除另一方（配合 R1 第七节级联扫描）
- 模板可保留可执行要点，但不得与规则原文冲突；冲突时以规则为准
- 教训一旦定稿为规则，就不在 `logs/lessons.md` 重复（改留"已定稿"指针即可）

## 整合检查（防碎片化）

- 新增规则前先查是否与现有 R1–R11 重叠；可合并 → 并入，**不新建**
- 确需新建 → 在规则内说明与现有规则的关系（补充/扩展/替代）
- 每轮规则变更后**同步更新 README 规则索引**

## 冲突裁决顺序

1. 优先级（frontmatter `priority`：high > medium）
2. 同优先级 → 用户明确意图优先（当面指示 > 规则默认）
3. 仍无法裁决 → 保守执行（不改文件、不输出不确定内容），向用户确认

## 常见冲突对

| 冲突对 | 裁决 |
|---|---|
| R1 精炼 vs R2 反驳需展开依据 | 反驳义务优先，依据精简至一行 |
| R5 肯定记录 vs R5 省 token | 记录必做，用增量 + 编号引用省 token |
| R3 咨询不修改 vs 用户语气含糊 | 一律按咨询处理，先确认 |
| R1 必修项直接改完（自治） vs R3 未授权不动文件 | R3 优先：未授权时只报告 + 给唯一最优改法；已授权范围内一律自治闭环 |
| R1 结构块③"其他方案与对比" vs R1 第二节"只给唯一最优解" | 默认只给最优解；仅用户要求对比或属 4 类请示情形时才列其他方案 |
| R2 挑剔原则（一丁点毛病也要挑） vs R1 第三节 P3（不必管不提不问） | 对象不同：R2 针对用户陈述；文档/代码中的无伤大雅项按 R1 分级，P3 不报 |
