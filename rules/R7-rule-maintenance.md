# R7 规则维护

## 命名约定

- 任何"字母数字代指简称"（如 R1、SKILL-A）一旦用于指代文件，**必须**作为该文件名的前缀
- 目的：打开目录即识别文件身份，无需打开文件才知道简称含义
- 示例：`R1-output.md`；无简称文件不受影响（如 `context/project-context.md`）

## 自动积累（触发）

- 项目/功能开发过程中，遇到**有用且通用**的规则限制（AI 发现或用户指出），自动补充入 ai-rules，不等提醒

## 归置判断

- **通用**（跨项目/跨功能适用）→ 写入 `rules/`：新建 `R<编号>-<kebab>.md` 或并入现有规则
- **专用**（仅当前项目/功能有效）→ 写入 `dev-docs/<项目名>/features/<功能名>/feature.md`，不入 ai-rules

## 整合检查（防碎片化）

- 新增规则前，先检查是否与现有规则（R1–R10）重叠或可合并
- 可合并 → 并入现有规则文件，**不新建**
- 确需新建 → 在规则内说明与现有规则的关系（补充/扩展/替代）
- 每轮规则变更后，**同步更新 README 规则索引**（防索引滞后）

## 冲突裁决顺序

1. 优先级（frontmatter `priority`：high > medium）
2. 同优先级 → 用户明确意图优先（用户当面指示 > 规则默认）
3. 仍无法裁决 → 保守执行（不修改文件、不输出不确定内容），向用户确认

## 常见冲突对

| 冲突对 | 裁决 |
|---|---|
| R1 精炼 vs R2 反驳需展开依据 | 反驳义务优先，依据精简至一行 |
| R5 肯定记录 vs R5 省 token | 记录必做，用增量 + 编号引用省 token |
| R3 咨询不修改 vs 用户语气含糊 | 一律按咨询处理，先确认（R3 已定） |
